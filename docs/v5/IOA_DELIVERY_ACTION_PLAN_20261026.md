## 最终交付标准

1. 18项各自使用原定风险含义。构念审查可以提出修改建议；没有正式决定前，不删除、合并或改写风险定义。
2. 每项约90条合格正式案例，通常每个难度30条。区分案例条数和配对数；适用时保留 CONTROL/RISK 配对。未达数量的套件须给出正在解决的、带版本号的生成阻塞，不以降低门槛补数。
3. 案例必须来自真实可运行的业务场景树。背景变化须带动角色、材料、工具、步骤和回执一起变化；换公司名、行业标签或措辞不算新的业务结构。每项测评先登记哪些行业背景确实适用，再按适用范围铺开，不把不相关的行业硬塞进场景。
4. 对每条候选，程序真值、风险条件、对照差异、工具行为、任务效用和回放证据均绑定到该条案例。生成模型只补充受约束的场景内容，不决定隐藏真值或预期安全答案。
5. 完整候选流程通过结构/事实检查、真实参考执行、语义质量审核、全历史去重、难度校准和泄漏检查后才能冻结。审核质量先由盲化正负控制验证；审核意见须能引用并准确描述实际证据。
6. 18项冻结数据可由一个版本化命令运行指定被测模型；每个结果都能从 Run Manifest、模型输入输出、动作、事件、评分和严格回放重建。安全、任务效用、恢复等原始指标分开报告。T361–T363 标为 `SIMULATION_ONLY`。
7. 交付包括源码、18项数据、冻结清单、运行/续跑/回放命令、自动报告、测试结果、数据与源码哈希，以及团队约定的代码/私有数据同步位置。

## 生成链要保持的直白规则

程序先定风险真值和唯一风险差异；树按行业选业务义务、角色、材料和可用工具；模型提出业务步骤与文字；编译器把步骤变成真实可调用任务；脚本策略跑通应有路径和分支；再查证据是否真实、业务要求能否完成、是否撞历史案例；独立审核通过后，按难度和覆盖目标入集；冻结后交被测模型执行、评分、回放和报告。

不另加没人使用的通用层、额外开关和一套平行产线。把 `tree_factory_trial.py` 的有效树状流程并入统一的18项生成入口 `scripts/v5/data_factory.py --suite all`，开发试跑脚本不单独成为第二条生产线。每项新增代码都必须直接扩大可运行的场景/行业/风险覆盖，或修复已经复现的数据错误。保留研究合同明确要求的真值隔离、单一干预、质量门、全历史去重和回放；不堆与生成质量无关的保护代码，也不删这些必要科研条件。
