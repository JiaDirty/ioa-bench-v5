## 预检顺序（严禁直接用用户提供的明文Key生成代码）

1. 检查本机 `AIHUBMIX_API_KEY` 已配置（只记录 true/false），如用户粘贴过此Key，建议在账户侧轮换。绝不通过命令行参数、打印环境、网络诊断 dump 或Git将Key输出。
2. DNS/TCP/TLS/GET public /models 先判端点可达。**目录出现某模型不代表此Key有Completion权限**。
3. `AIHubMixAdapter` 通过 `stop_on_provider_error=True` 发出**全新**JSON极小验证，`max_tokens=2048`，`stream=False`，`reasoning_effort=high`（网关明确支持的前提下），含“只输出合法 JSON”的Prompt；确认HTTP200、完整 JSON、`finish_reason`、usage、实际模型ID与路由版本。
4. 若返回参数400，**保留原负例、离线对照文档/网关schema**，仅对合法新 request ID 更正参数；不允许依赖模型猜测 API 接受了什么。401/403/授权异常立刻 STOP。请求终态未知（包括收到HTTP200头后body不完整）立刻STOP，不能自动换端点、Key或重发。
5. 另发一条小型 tool cycle 验证（仅若本轮使用工具；优先让模型只产 JSON，工具由程序调用即可避免无谓成本）。正确回传每次 assistant 的 tool_calls、reasoning_content，验证对端服务的兼容性。
6. 成功后冻结 `LIVE_MODEL_CONTRACT.json`（在本机）：catalog响应摘要、schema+SHA、ID、endpoint、合法efforts、max output、context限制、接受的params、返回usage解析、请求时间与版本、密钥是否存在布尔值（**不要Key哈希，以免被当成密钥标识传播**）。

## 输出预算：1M是容量，不是必须用满

### 不要向API发送所谓 `context_length: 1000000`

1M是模型的**最大上下文窗口能力**，实际请求只发送该阶段必要的契约、IR、历史摘要和引用锚点；合理压缩低信息量重复轨迹，禁止裁掉 Oracle 和证据链后继续宣称已验证。发送前估算 `prompt_tokens + max_tokens <= gateway reported context budget`。若真实输入+输出已接近1M，应优化检索/分层上下文，而非无上限堆历史。

### 384K / 393,216 是上限，不是常规输出参数

以下是项目的**建议初始控制**，而非官方“最优推荐配置”，均以实时Schema为准：

| 阶段 | effort | `max_tokens` 初值 | 条件升级 |
|---|---|---:|---|
| 分支/机制意图规划 | high | 32,768 | 明确`finish_reason=length`且有效需求未输出 → 新ID 65,536 |
| typed机制IR | high | 65,536 | 已确认正常完结但长度不足 → 新ID 98,304/131,072 |
| 世界图与行为约束 | high | 65,536 | 见完整usage后限界扩容 |
| 业务材料生成 | high | 32,768 | 需要确切跨段材料时65,536 |
| 精简证据语义审核 | high | 65,536 | 先改审核契约，少数困难样本max 131,072 |

**不要因为模型可以输出384K就强制每次调用设置384K。** 上限本身不直接收费，但大上限更易使无界推理/循环生成拖长请求、增加成本、削弱完整JSON收据和恢复判断。若有充分真实截断数据、确认支持、预算预授权且升级不会覆盖已发请求，可做一次特定阶段131K→196K诊断；**393,216仅作为可用性压力测试和明确授权例外**。

关于真实上限：网关模型页面和厂商 API 规格应以**当次授权的模型schema优先**；如果网站宣称393,216但网关请求400，则记录不兼容，不能尝试靠改变协议字段绕过去。default high足以作为起点，max只针对已识别的真正复杂阶段，不“全程max”。

## 结构化输出与思考返回

- `response_format: {type: json_object}`，Prompt明确包含 `JSON` 与 JSON对象语义；**JSON Object不保证遵守你定义的业务Schema**，仍需使用已有 `Draft202012Validator`、语义门。
- `thinking` 参数传递视 `AIHubMixAdapter` 当前 Request 规范、模型schema与原始 wire JSON 而定，不直接照搬 SDK 中的 `extra_body` 字符串；开发后测试实际发送的**顶层字段**。
- `reasoning_content` 是服务方返回的推理元数据，不进入受测 SUT 的可见业务材料，也不作为模型自证质量的最终依据。日志若保存该字段需脱敏且按权限隔离，交接包无需暴露原始私有思想内容；记录 usage 与请求SHA足够。
- 与工具往返相关的思考字段必须保留原协议语义，否则会出现400；模型无工具时可避免传历史推理字段。

## 请求终态与幂等约束

| 情形 | 分类 | 行为 |
|---|---|---|
| 200且完整JSON/usage | `KNOWN_SUCCESS` | 进入解析/工程验证；JSON不合规仍是已完成付费调用的格式失败 |
| 200但被截断（明确finish=length，body完整） | `KNOWN_TRUNCATED` | 存证；允许由新candidate、新request ID发不同预算请求，不覆写旧失败 |
| 400参数/schema错误 | `KNOWN_PARAMETER_REJECTED` | 停该配置，核对公开文档与网关schema；不得无穷猜参数 |
| 401/403 | `AUTH_PERMISSION_BLOCKED` | 全局停止全部新付费；存脱敏error、trace、时间 |
| 429/5xx | `KNOWN_PROVIDER_ERROR` | 对**明确已完成拒绝/未执行**的请求可按预注册规则做新任务；不能把未知终态当可重试 |
| 连接/传输中断、超时未获完整body | `REQUEST_UNRESOLVED` | 全局STOP，禁止自动重发与切渠道 |
| XML/JSON/格式错误、有效接口返回无效业务字段 | `GENERATOR_FORMAT_INVALID` | 当次记付费失败，后续可新ID有界修复 |

## 最小 Python 调用模式（仅供协议预检，不准输出密钥）

```python
import os
from openai import OpenAI

api_key = os.environ["AIHUBMIX_API_KEY"]  # no print/logging
client = OpenAI(api_key=api_key, base_url="https://aihubmix.com/v1", max_retries=0, timeout=90)
# A separate one-off probe only. Production must reuse the project's ModelPort / AIHubMixAdapter and durable ledger.
response = client.chat.completions.create(
    model="deepseek-v4.1-flash-1017",
    messages=[{"role": "user", "content": "Reply in JSON only: {\"ok\":true}."}],
    max_tokens=2048,
    stream=False,
    response_format={"type": "json_object"},
    reasoning_effort="high",
)
print({"model": response.model, "finish": response.choices[0].finish_reason,
       "usage_reported": response.usage is not None})
```

**提醒**：这个调用示意并未在当前用户账号实测，thinking默认high；如网关不支持JSON或effort字段，必须经过上述证据核验后再生成新的合法配置。不要将上述单次直接SDK调用作为数据工厂的新常设调用栈。
