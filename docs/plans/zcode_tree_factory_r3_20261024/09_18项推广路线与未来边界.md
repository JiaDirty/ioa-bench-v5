# 09 · 从三套件研发试点到18项：用可移植能力而不是复制代码

本轮的“通用”指**业务组合层接口可复用**，不是声称剩余15项已经支持通用 DAG。R3 不能为了表面18项覆盖率而复制18个 `business_binding_t3xx.py`。

## 四级能力状态（分别填写）

每套件给出：

1. `CATALOG_READY`：有哪些行业/工具模块是合法业务能力？
2. `COMPILER_READY`：能否将新 workflow plan 经 MechanismIR 和该 suite 既有 compiler compile？
3. `RUNTIME_WITNESSED`：实际工具、角色授权、事件/证据链是否完整？
4. `DEV_POOL_VERIFIED`：是否至少有实际历史不重复研发入池数据，且多样性图谱可核证？

任何未实测项使用 `NOT_IMPLEMENTED / UNSUPPORTED / NOT_RUN`，不把“共享模块已经存在”算成“18项全部具备”。

## 推荐迁移顺序

- **第一层**：本轮 T321（协商与时序）、T331（级联传播）、T362（讨论与证据释放），覆盖不同机制行为；优先补业务 DAG 的 stage/role/event 真实性。
- **第二层下一轮**：选一个业务参与者、工具/证据模式**明显不同**的代表套件，例如 T352（声誉/治理）或 T332（级联其他结构），依据当前 HEAD 真实 suite 编译器和测评构念选择一个先打通；**本轮只要求接口适配清单，不要求真实生产第四套件新数据**。T352 旧样本工具回执不一致有历史教训，先读保留证据再试。
- **第三层**：剩余测评按风险机制所需运行时能力（自治多角色、工具授权、证据传播、时间调度、恢复）分组复用 runtime hooks；每批适配少数而不是一口气全部18项。

## 可复用契约推荐

`SuiteWorkflowCapabilities` 应答：可承载哪类阶段/工具、哪些受测 actors 固定、哪些 NPC actor 可合法确定性调度、role isolation 能否实现、事件发布/消费 hook、证据可见规则、配对干预槽、原 construct 保真测试 ID、当前支持 workflow schema 版本、未支持点。

**唯一科学红线**：本轮不能通过增加角色/工具，改变 T321 等套件的规范化风险测评任务、合法任务完成定义或干预/评分器边界。若某套件机制不适合业务 DAG，允许返回结构受限或“暂无适配”，不要为了数据量勉强增加无关业务片段。

## 长期数据生成质量方向

将结构覆盖、质量反馈、历史最近邻、失败类别反喂 planner，用**覆盖引导的可执行工作流搜索**逐轮寻找此前未覆盖的合法结构；可把各行业原子模块作为可验证语义库。不要引入原生任意代码执行以追求“开放式”；我们追求的是**模块语法下多样化且逻辑自洽的组合**，有能力说明新组合与旧结构区别。
