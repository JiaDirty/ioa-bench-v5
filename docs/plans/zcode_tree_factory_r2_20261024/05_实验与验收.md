# R2：让“确实更好”成为可测试的结果

## A. 四组必须先绿的反事实（离线，不花 Token）

1. **真实业务联动**：同一 T331 提案/拓扑/seed，选择 medicine 与 finance：`business_context`、编译 world 的角色/权限/资产/工具、工具行为、业务事件 DAG 应存在**非同名替换**的差异；必须有引用到真实 runtime trace 的 witness。不能仅凭场景文本差异 PASS。
2. **同树配对一致性**：固定一个 `BusinessBinding` 和完整 IR，CONTROL/RISK 只能变声明风险槽；角色/资产/非风险工具行为一致，且参考策略双臂可合法完成任务，因果违规/恢复观察按原硬门计算。
3. **IR 必经与非法拒绝**：零 agents、事件依赖环、无对应 role 的工具、悬空 evidence ID、跨域权限、跨行业工具、干预槽不唯一，逐例 `validate()`、projection、在线新路线均 fail。用 spy/依赖图证明新候选不能跳过 IR。
4. **结构区别不是换词**：只改行业名称、代理名字、表面材料、seed，不导致 `mechanism_graph_hash` 变化；实际改变拓扑、时序门控或证据依赖，必须有被执行 witness 的机制图变化。业务图 hash 则应该识别真正不同的业务流程。

## B. 三层多样性独立度量

每条候选至少报三个 hash，需说明 canonicalization 使用的数据与同构判定范围：

- `instance_hash`：最终文本、非秘密场景素材、业务细节的实例级区分；服从原历史近重复 0.9 门。
- `business_workflow_hash`：抽象掉行业名和角色 ID 后，保留**实际参与者角色、工具能力/权限、资产/证据、业务义务、事件 DAG**。不能把纯行业换词当新流程。
- `mechanism_graph_hash`：保留原风险构念、执行中的拓扑、时序/干预/回执因果边、证据传播与相互作用；忽略名称、背景、seed。必须从编译后的结构**及真实执行证据**交叉生成，不仅靠 LLM JSON 声明。

同一 `mechanism_graph_hash` 的两个候选都可以是合法的研发实例（如果原实例去重通过），**绝不能把它们说成两种新机制**。既有 T362-t2-T/T362-t2-B 的同签名事实保持原样。

## C. 在线最小实验计划（新 ID，不复用18个旧单位）

- 试点 T321/T331/T362，各至少2个目标结构/任务种子，**旧 G2 和新完整 Tree+IR**各获得一个同题机会。先处理 T321，得到一对可入池后再并行跑其他套件。推荐增加到每套件3个任务以避免偶然好坏；实际投入可以更高，不受费用限制。
- 新/旧路线使用**同一AIHubMix模型、相同审核协议、相同合法输出档位、同一工程门、同一个历史索引快照**；旧路线四阶段 vs 新路线阶段不同就明确只能评价**系统整体有效率**，不能声称树/IR单独因果效应。
- 离线两因素消融（T on/off × IR on/off）先证明功能性：工具绑定、IR非法输入拦截、执行图变异来源。若做在线两因素的因果比较，则需要另外冻结四臂等价调用阶段、提示长度与任务分配；本轮先不凭劣质统计抢结论。
- 每个目标都要有**全部运行机会**的行：成功、硬门拒收、模型真实终态错误、已知截断、未知、历史重复、审核合同无效、分歧、入池。未执行明确 `NOT_RUN`。

## D. 审核校准

程序离线校准：沿用18负例/6正例、保留冻结数据；加入至少12条未见的不同反例（无效事实 claim、假 evidence 引用、交叉套件干扰、无真实业务工具、Oracle泄漏、单臂、历史近重复等）与至少6个有效正例。程序事实/合同层**不允许假接受已知违反硬条件的候选**，同时不能把正例全拒。

真实模型审核：两个隔离上下文 `high/max`，记录各自可解析率、有效证据引用率、合同通过率、与程序真值一致率、双方分歧/拒收，保留原始回复和具体证据。严格区分 **离线规则校准通过** 与 **模型审核语义能力已被实证证明**。同模型审核依然仅供开发筛选。

## E. 对比的最小指标

1. `new_generated_pairs / all_new_generation_attempts`、`engineering_pass / all_new_generation_attempts`、`new_DEV_ACCEPTED / all_new_generation_attempts`；按 suite × route 分开。
2. `design_execution_fidelity_rate`（预先声明的每条关键结构断言有运行时 witness 的比例）、失败原因分布。
3. `unique_business_workflow_hashes`、`unique_mechanism_graph_hashes`、`accepted_instances` 三列独立输出。
4. `full_response_rate`、`finish_length_rate`、`known_transport_failure`、`unresolved_post_count`，分母包括失败；真实 token/延迟/费用只做诊断，不按省钱排序。
5. `audit_format_pass / audit_attempts`、`audit_semantic_disagreement / paired_audits`、`hard_gate_false_accept=0`（已知测试集限定）、真实新正例不被误拒。
6. 18项扩展：输出每项已注册运行时能力、当前候选数、已接受实例数、唯一机制数、剩余 capability gap；T322 保留 `VERSION_SCOPED`/历史5.1.0的120条缺口。

## F. 单个新 `DEV_ACCEPTED` 的最低证据

`TASK.json`、`BUSINESS_BINDING.json`、`MECHANISM_IR.json`、`IR_VALIDATION.json`、`COMPILER_BINDINGS.json`、`BLUEPRINT.json`、`COMPILED_CONTROL.json`/`COMPILED_RISK.json`（可采用项目现有文件格式）、`EXECUTION_WITNESSES.jsonl`、`HARD_GATE.json`、`HISTORY_DEDUP.json`、`STRICT_REPLAY.json`、high/max各自完整 `AUDIT_RESULT`、`RESULT.json`、源码/runtime hash与 model request receipts。文件名可以映射现有约定，但内容不可缺失。

**实验成功定义**：R2 的每项试点至少一对真实新接受，且设计—业务执行联动达标；在此之前只叫 `PARTIAL`，不能为凑数接受不合格样本。
