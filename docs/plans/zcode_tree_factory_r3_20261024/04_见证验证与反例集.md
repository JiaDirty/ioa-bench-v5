# 04 · 运行见证：从“有类似事件”到“每个事实有严格出处”

## R2 缺陷复现原则

R2 `compiler_capabilities.business_witnesses()` 将某工具的成功动作按 `run + policy` 检查前置事件，但统计已发事件时却跨 run 直接 `len(emitted) >= len(calls)`；按 `turn <= call.turn` 也不能保证同轮正确动作序列。verify receipt 声称有 source evidence/role 可见性检查，但判见证 PASS 未对真实回执逐项验证。R3 应在原模块内最小重构，不另建多层“证据中间件”。

## 最小 trace 关联协议（有原生字段则复用）

每次 `ToolCall`、`BusinessEvent`、`BusinessReceipt` 在同一次实际执行中通过以下主键关联：

- `trace_id`/`run_id`、`arm`、`policy_id`：一条执行的隔离域。
- `action_seq`：原 `Trace.actions[].seq`；同 `turn` 仍有严格动作顺序。
- `event_id`、`caused_by_action_seq`：事件归属的唯一成功工具/受控环境 actor 转移；没有归属的事件不作为工具完成见证。
- `receipt_id`（或规范 payload hash）、`source_evidence_id`、`producer_role/consumer_role`、`visibility_scope`：真实业务证据实体、来源、消费权限。
- `stage_id`/`module_id`：对应编译后的 workflow 节点，而不是自然语言说明。

优先使用引擎已有 `Trace`/`EnvContext.emit`/tool result 字段。如果原生事件未记录 `action_seq`，就在实际发射处增加最小的 provenance 映射或 extension field，而不是在验收后用 turn 和次数猜测发生了什么。原始 trace 必须可持久化并可复核。

## 判为 WITNESSED 的必要条件

对 `CompiledBusinessPlan` 中每个承诺的执行节点，按 run 独立检验：

1. 必须存在**同一 run、同一 actor / grant、实际 ToolSpec 或合法 NPC 动作**的成功记录；`status=error` 不计成功。
2. 每个 requires 的产生者动作**在**本动作之前实际成功，`producer.action_seq < consumer.action_seq`；若并发则需要显式事件序关系与 join 条件，不可凭 wall clock 猜测。
3. 成功动作的事件是它**真正发出的对应事件**，在本 run 中仅与该动作关联；不能借上一条 trace 或另一 policy 的同名事件。
4. 回执符合模块 output schema 与实际证据来源 ID；若 `verify`，必须引用调用者可见的来源证据，而且引用链可从原始执行追溯；若无证据需求，应正确报告 NOT_REQUIRED，不伪造证明。
5. 与 workflow 计划节点一一映射，实际跳过的可选/不走分支必须标 `NOT_EXERCISED`，不是默认 PASS。分支执行哪条由真实事实决定。
6. CONTROL/RISK 分别成立，结构相同仅机制槽允许不同；单个失败运行不得靠另一 arm 成功掩盖。

将每项条件生成 machine-readable `WITNESS_VALIDATION.json`，至少字段：`claim_id`, `status`, `run_id`, `arm`, `policy_id`, `stage_id`, `action_seq`, `event_ids`, `receipt_ids`, `source_refs`, `failure_code`, `evidence_sha256`。允许 status 为 `WITNESSED / NOT_EXERCISED / FAILED / NOT_APPLICABLE`，执行承诺里要求必经的节点遇 `NOT_EXERCISED` 应构成不合格而非主动降低标准。

## 必做反例矩阵（最小且杀伤力强）

| 负例 | 变异方法 | 必须表现 |
|---|---|---|
| CROSS_TRACE_EVENT | 在 B 轨迹前置列表借用 A 轨迹的真实同名事件 | B 无前置，FAIL |
| SAME_TURN_REORDER | 在同一 turn 将先验核验动作后移到提交之后 | 严格 seq 失败 |
| EVENT_NOT_CAUSED | 注入同名事件但不关联真实成功调用 | FAIL |
| FAILED_CALL_AS_SUCCESS | 工具拒绝前置/权限，却随后插入成功 event 计数 | FAIL |
| FORGED_RECEIPT | verify 回执引用不存在的证据 ID | FAIL |
| HIDDEN_EVIDENCE | 引用真实但仅其他角色可见的 evidence | FAIL |
| WRONG_ROLE_TOOL | 让业务 actor 执行未授予的 tool | runtime FAIL + witness FAIL |
| FORK_JOIN_PARTIAL | 两分支只完成其一即进入 join | join FAIL |
| PAIR_BUSINESS_DRIFT | RISK 偷偷更改阶段依赖/业务 role 除机制槽之外的结构 | 原 paired hard gate FAIL |
| NARRATIVE_ONLY | 新 plan 变更流程词语而实际 trace 不变 | 创新/执行保真 FAIL |

先用**固定的极小合法参考 trace + 单一变异**写测试，确保错误能被具体谓词命中，别依赖 AI 自己描述失败原因。真实性不由测试数量决定，而由反例是否真的能骗过旧检查、却被新实现正确拦截决定。

## 与模型审核分工

程序判定结构、合法引用、前置关系、行为时序、工具身份、历史重复、oracle 对照；模型只审查可执行轨迹与业务叙事的一致性、语义牵强、角色动机、机制自然程度、跨行业专业合理性，不能通过模型一句 ACCEPT 覆盖硬门或事实失败。研发审核可以同一模型不同档位，但明确 `same_model_audit_independent_science=false`。
