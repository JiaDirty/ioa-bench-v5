# 08 · 真实验收、回归、Git、交接

## 总则

本轮交付不是“新建了 WorkflowPlan 类、测试绿、模型给出 ACCEPT”就完。只有**最终 HEAD、实际新样本的可执行证据、失败分母与复验路径一致**才过。

## 最小验收矩阵

| 验收 | 必须有的直接证据 | 不接受的替代 |
|---|---|---|
| HEAD与旧进度对账 | `git rev-parse HEAD` + 对账报告 + 已冻结 R1/R2 IDs | 以旧 SOURCE 打包时的短 SHA 充数 |
| T321 多阶段 | 实际 CONTROL/RISK 工具动作、事件、回执、≥3阶段≥2逻辑角色的可见授权前置 | 3条提示词/3个静态 stage 列表 |
| DAG生成/消费 | 原模型 WorkflowPlan、绑定 compiler、IR、runtime action 与变更后的完整图 | 规划示意图/手工塞固定 workflow |
| WITNESS | 每一要求节点的同 trace/seq/actor/证据引用，以及专门负例 | `len(emitted)>=len(calls)`/模型评论 |
| 本轮新家族 | 三套件各至少两种新合法图；与 R1/R2 历史归一比较+真实运行 | 行业换名/节点重命名/同图不同实例 |
| DEV_ACCEPTED | 三套件每套≥2本轮全新配对、硬门+reference+replay+去重+研发审核原文 | 研发候选/一臂通过/报告自称通过 |
| A/B | 预先冻结、各套件≥6个 matched opportunities、两路线全分母、补救行独立 | 事后改条件后只选成功结果 |
| 回归 | 最终 HEAD 上的原 suite 测试及新负例，JUnit/命令/环境，独立关键回放 | R2 1928 的历史 JUnit |
| 历史保护 | 核实文件范围/总数/实际逐文件 hash 个数，误差与例外清楚 | `files_checked=0` 但宣称18万文件新核实 |
| 交付完整性 | 两份 ZIP 全量 CRC+成员 SHA、凭据扫描、差异说明 | 只附 Summary；源码和日志不同 HEAD |

## 必须做的针对性运行测试

**不需要人为新增几千个单测**；核心是以下能真正杀死错误的测试：

1. `test_t321_multistage_control_risk_reference` 验证真实3阶段以上、两逻辑角色、严格 Replay、原 T321 construct；
2. `test_illegal_early_join_rejected`, `test_cross_role_evidence_denied` 触发 runtime 拒绝；
3. `test_model_plan_not_in_static_business_flow_compiles`，并与 R2 静态图作归一非同构；
4. `test_tree_change_modifies_runtime_and_not_truth`：行业改变业务工具与证据，但不改变 oracle/risk slot；
5. `test_workflow_rename_does_not_create_new_family`；
6. `test_business_witness_cross_trace_spoof_rejected`、`test_same_turn_reorder_rejected`、`test_fake_receipt_rejected`、`test_failed_call_not_counted`；
7. `test_r2_backward_compatibility` 兼容先前10对 R2 样本与现有评分/历史快照；只读重放，不改历史原始结果；
8. `test_r3_resume_offline_does_not_call_provider` 原有 UNKNOWN 不重发；
9. 将新增测试纳入项目现有 pytest 配置，完整命令/失败/固定版本目录记入交接。

## 两个 ZIP 的准确范围

建议本机输出到 `exports/tree-factory-r3-review-20261024/`：

- `IoA-Bench-v5-TreeFactory-R3-SOURCE.zip`：final HEAD 全量 git archive（已排除凭据），与 R2 的 diff，新增 tests/config/schema/docs/plans/准确 Git log/status；特别含 runtime consumer，不能只打包新增类。
- `IoA-Bench-v5-TreeFactory-R3-EVIDENCE.zip`：R3 run 中**全部**候选/模型请求/程序验证/成功/失败/UNKNOWN/审核意见/A-B原始数据/消融/strict Replay/JUnit/必要历史去重索引与哈希证明。体积大可分卷并索引，不得只挑 DEV_ACCEPTED。
- `TECHNICAL_REVIEW_HANDOFF_R3.md`：Goal逐项、真实成果、未达到的目标、风险、精确路径+证据ID。
- `FILE_SHA256.json`、`PACKAGE_VERIFICATION.json`、`REVIEW_FILE_INDEX.json`。

不需要复制18万份历史文件，但**必须**实际验证当前声称保护的范围并附清单哈希/抽检或全量的具体分母。缺材料的历史测试按 `NOT_RUN / ENV_BLOCKED` 写清楚，不能写 PASS。对比模型/工作流历史判重所需的精确索引建议一并收入证据包。

```
HEAD_FULL_SHA / BASELINE_SHA / branch / git status
R3-G0...G7: PASS | PARTIAL | BLOCKED | NOT_RUN + evidence paths
Actual R3 DEV_ACCEPTED: T321=?, T331=?, T362=?; per-suite unique novel families=?
T321 proof: stage counts / actor roles / evidence chain IDs
Proposed DAG examples: model response ↔ plan ↔ IR ↔ blueprint ↔ action/event receipts
R3 AB: frozen opportunity counts; treatment first-pass accepted; baseline first-pass accepted;
       repairs, rejected, unknown, audit disputes; confidence/limitations
Provider: intents / confirmed complete / length / transport unknown / auth errors; usage
Tests: final HEAD / command / passed-failed-skipped / JUnit path
History protection: protected universe / checked / mismatch / exclusions
Artifacts: SOURCE ZIP path+bytes+sha256; EVIDENCE ZIP path+bytes+sha256
Unresolved critical blockers; scientific review status independent=false
```

若外部接口暂不可用：先把本地 G1/G2/G3 全部做实、提供离线正反事实 trace 与真实技术阻塞，不谎报 G5 或 G6。待新 ID 可用时再继续；原已发未决请求永不重发。
