## 赶进度的执行顺序

1. **先准备可展示的完整案例。** 从已保留的真实生成候选中选医疗、支付、物流代表例，逐份核对原始计划、业务步骤、正常/风险对照、运行动作、评分和拒绝/隔离原因。展示两种真实流程结构，避免只展示换公司名、换数字的样本。不能补写不存在的审核结论。
2. **复用已跑通的小批流程。** R19已完成4对；新接套件先做小批生成、检查、两次独立上下文研发审核和结果留存。每个机会记录成功、拒绝、隔离或未运行，历史未知请求永不重发；这两轮同模型审核不等于独立科研资格。
3. **接入剩余路线。** 代表资格漂移已完成中介与执行者实际交接的工程验收；接着做结构暴露、行为推断、谣言扩散、生态错误共识、判断让渡、能动性弱化。互操作失配的原始历史合同缺口另行跟踪；不要反复搜索已经查过的相同归档。若分工并行，按模块划定文件所有权，主线负责代码整合和当前源码验收。接入项必须给出实际动作和回放。
4. **集中验收后再扩量。** 开发时先跑受影响测试，多路整合后做一次全量回归和精确源码回放。完成小批实测与质量核验后，再按业务结构缺口扩量，并开展难度校准、版本冻结和18项全量评测。

汇报材料包括准确进度表、可打开的完整案例、真实批次结果及下一批接入验收条件。正式交付仍要求18项数据、真实被测模型结果、评分、回放与报告全部齐全。

暂缓无直接收益的新框架、重复重构、额外包装和反复全量测试。保留必要的事实检查、隐藏真值隔离、请求记录、质量检查和回放。测试数用来证明改动没破坏程序，不能替代数据产出数。
