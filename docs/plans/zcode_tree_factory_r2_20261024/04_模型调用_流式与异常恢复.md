- 指定 URL：`https://aihubmix.com/model/deepseek-v4.1-flash-1017`；指定 API model ID：`deepseek-v4.1-flash-1017`。工作区已存在 Chat Completions 适配器和 SSE 流式实现，**先用它，禁止再造新 HTTP client**。

- 旧 G1 JSON 预检 `receipt_value_exact=false`，但脚本未把它算作失败。新的 G1 应将“传输与身份有效”和“模型精确遵循 JSON 合同”分别验证，精确错误不能冒充 auth fault。

## 2. 最大输出怎么使用才最高效

**建议参数**：通常复杂阶段 `max_tokens=131072`，极复杂业务图/因果设计或语义审核 `262144`；如果需要且网关实际允许，自动开放到 `393216`（遇上限只接受384000等情况，选择实测值）。并非每一阶段都要 max/max；我们追求**首次得到完整有效 JSON 的概率**与真实入池率。

先做一次**很短输出**的参数上限探针：设超大 `max_tokens` 但只要求几十 Token JSON，检查 HTTP/served/参数校验，不能把大上限探针当作“长达384K生成已稳定”的证明。旧探针只能保留，不可重发。成功后在少量真实业务任务中分阶段观察 `reasoning_tokens`、最终 JSON 长度、SSE 活跃间隔、最后 `finish_reason`，选择最省浪费的宽松档，不按成本优化。

成功路径：合法 JSON → schema → IR → compile → execute → audit。任何 `finish=length` 但正文不完整，都不得作成功候选；应先判断是输入过长、内部推理耗尽还是需要拆解阶段。优先**把复杂任务拆成逻辑完整、可独立验证的两段**，而不是在一个容易断流的连接上无限拉长推理。

## 3. 简洁的传输/终态分类与直接动作

| 情况 | 意义与处理 |
|---|---|
| HTTP200 + SSE完整终止 + JSON合格 + usage | `REQUEST_FINISHED`；推进下一阶段 |
| HTTP200 + 明确 `finish_reason=length` | `KNOWN_TRUNCATED`，保存完整响应；用新 ID、提高合法上限或缩小目标拆分新候选 |
| 合法 HTTP400：`max_tokens` 超范围 | `PARAMETER_REJECTED`，该请求已确定失败，记录并在新的参数探针上选较小合法 ceiling |
| HTTP401/403、模型权限无效 | `AUTH/PERMISSION`；停止新在线调用，继续离线工作，不猜测秘钥 |
| SSE/网络中断、已经发 POST、无法确认服务端是否完成 | `REQUEST_UNRESOLVED`；旧 ID 永不重发，**隔离该任务**；其他全新、可区分且完成健康检查的任务可以新 run 继续，不继承旧 STOP 的假成功状态 |
| 明确未发送 POST 就已因 DNS/TLS 报错 | `PRE_SEND_FAILURE`，修复网络路径后全新任务可继续 |
| JSON格式/Schema 错误，但有完整终态 | `FORMAT_FIXABLE`，只用原错误和冻结期望做一次新 ID 修复，不覆盖旧回执 |
| high / max 对事实有冲突 | 确定性事实胜出，合同错误修复后新 ID；无法裁决的语义分歧隔离，不循环刷模型直到接受 |

不要无限自动重试、不给未知请求重新起同义 ID 变相重发。不能关闭已有账本或删除历史 unknown；**要允许新一轮独立工作继续推进**，不因早已失败的旧任务无限空转。

## 4. 审核：少传重复日志，多传可核实事实

开发审核输入分成三层：

1. 程序事实表 `facts`：配对完整、单干预、Oracle/历史/Replay结果、设计与执行见证摘要、引用来源与哈希。
2. 人可读业务解释：任务目标/业务义务/实际工具链/风险关联，来自编译后的可见 runtime，而非 LLM 自称实现。
3. 按需有边界的原始 trace 片段：每个 assertion 的 witness/ref id、JSON pointer、原始哈希和最少对应事件。必要时可从完整保留证据中定位，模型不需要吞下几十MB重复 log。

模型回答固定结构化短结论，`ACCEPT/REJECT/UNCERTAIN` 加 evidence pointers；禁止超长无必要议论文。**大 Token 上限只用于防止截断，不能把“回答越长”当质量越好。** 审核合同有效≠独立科学正确；仍使用两个隔离请求的研发审核。

## 5. 轻量并发与恢复

- 并发先 1（先通完整 T321 的最小批），稳定后 2–3；以**网关真实 SSE 完成率和账本正确性**调并发，不怕成本但避免并发造成大量未知请求。
- 新 R2 运行继续使用 append-only 请求账本；每个候选完整文件上下文绑定 request ID/源代码 hash/参数/response hash。
- 禁网 Resume 不再调用 provider；重复读取同一 request 只能返回已有完整缓存结果，不会创造新 completion。
