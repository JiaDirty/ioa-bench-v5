# R2 最小架构改造：把现有原型变成真正主链

## 1. 现有确认事实（基线 HEAD `49d096e`）

- `src/ioabench/v5/ai_generation/tree_factory.py::treatment_messages()` 调用 `business_context()`，但 `assemble_blueprint()` 只合成 `suite_payload`，没有将选择出的角色、业务义务、工具与真实事件映射到编译器。相同 proposal/seed/target 切换医药/金融，旧代码编译蓝图相同。
- `run_task()` 新路线 `propose_payload → assemble_blueprint → engineering_checks`，**没有走** `MechanismIR`。`mechanism_ir.py::blueprint_from_ir()` 旧实现只拦少数 `validate()` 错误，零 agents 或循环依赖也可能投影成功。
- `aihubmix_study.py::parameters()` 已经使用 SSE，但调用链仍出现 16K、32K 和64K输出；`check_budget` 仍执行 USD 5软/20硬停。
- `development_audit.py::audit_packet` 只允许审核输出 `16384/32768/65536`，新复杂审核往往因推理占满预算而无法给出足量 JSON。
- 当前已通过的6个新执行因子：T331 `rebroadcast_timing/confirmation_loop`，T321 `close_gate/renegotiation_window`，T362 `source_release/relay_before_digest`。**保留这些真实能力，不重写一套平行 slice。**

## 2. 唯一正常主链（应体现在源码 call graph 中）

```text
suite + coverage target + seed
  -> ScenarioBranchTree.select
  -> BusinessBinding.compile(selection)      # typed 角色/任务/资产/工具/证据/事件/边
  -> candidate MechanismIR (candidate + program-owned fields)
  -> MechanismIR.validate() == []             # 每次投影前都执行完整验证
  -> CompilerCapability.validate(binding, ir)
  -> blueprint_from_ir(ir, business_binding)
  -> existing suite adapter.validate_blueprint
  -> existing bounded compiler CONTROL/RISK (same business_binding)
  -> existing scenario/slice reference traces and execution witness
  -> existing causal/Oracle/firewall/dedup/replay hard gates
  -> facts + compact evidence packet -> two dev audits -> DEV_ACCEPTED
```

IR 和 BusinessBinding 是这条链的**必需输入**；不能单纯把 IR 保存成报告文件，或只把 business package 注入 Prompt。保留旧 `baseline_4stage` 完整只读对照路径，新增 `tree_ir_runtime_v2` 作为默认开发路线。

## 3. 最小数据契约——不引入第二套运行时

建议新增 typed `BusinessBinding`（可直接在 `scenario_tree.py` 或紧邻模块实现，避免目录爆炸）：

```python
@dataclass(frozen=True)
class BusinessBinding:
    root: str
    obligation_ids: tuple[str, ...]
    role_bindings: tuple[RoleBinding, ...]     # logical role -> runtime agent ID
    asset_bindings: tuple[AssetBinding, ...]   # logical asset -> world data/record
    tool_bindings: tuple[ToolBinding, ...]     # tool capability -> callable existing adapter tool
    evidence_bindings: tuple[EvidenceBinding, ...]
    event_dag: tuple[BusinessEvent, ...]       # visible prerequisite and temporal edges
    required_runtime_observations: tuple[WitnessClaim, ...]
    canonical_workflow_hash: str
```

字段名称可依项目命名调整，但不可只保留标签/行业字符串。所有绑定都必须有**编译出口和消费见证**。声明某个药房工具却没有对应 runtime tool 或可映射动作时，立即返回 `CAPABILITY_GAP`；不允许输出文字假装它已部署。

`MechanismIR` 是**当前候选的权威结构化表示**：业务绑定与机制因子、数据来源、权限和事件依赖必须相互引用；`oracle/scorer/expected_answer` 只由程序生成。先验证完整 IR，再投影到旧编译器；保留旧 schema、Oracle/scorer 兼容性。避免把模型生成的任意脚本在宿主机执行。

## 5. 真正的上下游联动，不是字符串游戏

**T331 医药分支**可以从“补货请求→药房核验库存→配送/供应商确认→库存回执”的合成业务义务链派生 agent、工具、资产与证据；**金融分支**可以从“清算指令→风控核验→对账→结算回执”派生。两个分支必须映射到已实现的 synthetic callable tool，必须有不同真实工具事件和数据依赖，且沿用同一风险构念“跨系统级联错误传播”。

强制生成两类测试：

A. **行业切换反事实**（不同场景，不是风险配对）：固定 mechanism topology/seed，把 root 从 medicine 切到 finance，断言编译业务流的 runtime 工具、agent 权限、资产与事件因果边真的不同，且两者各自可编译/执行/回放。

B. **单干预配对反事实**（同一场景的 CONTROL/RISK）：固定同一完整 BusinessBinding/IR 和随机源，只更改被声明的风险槽；程序证明其余 world/projected business/agent/tool 配置一致，两个参考运行和 Oracle 边界都合法。

`business_context` 可以继续用于 Prompt，但**不能作为业务联动通过的验收证据**。

## 6. 高效失败反馈

只允许三种明确的后续动作：

- `FORMAT_FIXABLE`（JSON/字段缺失）：保留失败，给最小 schema 错误及目标字段，在**新请求 ID**补一次结构化响应；被证明纯截断时用更大 `max_tokens` 的新请求，新 candidate lineage 绑定旧失败。
- `CAPABILITY_GAP`：无需再调模型，先补通用 registry/编译能力或把未支持单元送后续 backlog。禁止尝试换行业或改名骗过校验。
- `SEMANTIC_OR_FIDELITY_FAIL`：用程序事实+最短失败见证回馈，模型重规划**新 IR**，最多2次不同候选；每次完整重新跑硬门，不能偷改评分器。

已发送请求的终态不明一律不再发送**该请求**；不需要为一个旧坏 ID 无限阻塞其他新、可独立复核任务。

## 7. 拒绝过度架构

不要重新实现 ModelPort、provider SDK、runtime engine、trace format、历史索引、审阅系统的整个新版本；只补缺失的类型映射和消费链。无需为每个字段加三层 adapter/fallback；不保留多个“可选 IR 模式”导致新路径悄悄退回旧蓝图。优先做到一个可信完整 happy path，再补针对真实失败的负例。
