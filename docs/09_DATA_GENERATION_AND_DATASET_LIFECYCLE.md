# 09 — Data Generation and Dataset Lifecycle

## 1. Principle

There are 18 independent datasets, one per Txxx suite, generated by a shared automated framework. Formal benchmark data is not manually authored. Programmatic builders establish causal structure and truth; AIHubMix models enrich natural language and semantic diversity.

## 2. Generation architecture

```text
DatasetManifest
   ↓
MechanismTemplate + World + Difficulty target
   ↓
Programmatic Case Skeleton + Oracle Truth
   ↓
Generator Model Router (AIHubMix)
   ↓
Candidate Case
   ↓
Schema Validator
   ↓
Deterministic Invariant Validator
   ↓
Independent Semantic Validator
   ↓
(optional) second Validator / Arbitration
   ↓
Repair once when appropriate OR regenerate
   ↓
Deduplication / leakage check
   ↓
Difficulty calibration / distribution check
   ↓
Candidate accepted
   ↓
Freeze Dataset Version
```

## 3. Dataset target

v1 target per suite: 90 qualified cases, normally 30 Easy / 30 Medium / 30 Hard. Generate roughly 150–200+ candidates as needed; quota is on qualified cases, not raw outputs.

If a stratum cannot reach quota, the pipeline must diagnose failure reasons and improve templates/prompts/model routing/calibration. It must not weaken quality gates.

## 4. Generator categories

Use procedural generation for:
- identities, capabilities, organizations;
- delegation graphs;
- topology/workflow structure;
- protocol state tables;
- reputation/incentive numeric state;
- Ground Truth and expected invariants.

Use model generation for:
- business narrative;
- agent/public descriptions;
- messages/evidence/paraphrases;
- plausible distractors;
- rumor/norm variants;
- synthetic persona language;
- task naturalization.

## 5. Validators

### 5.1 Deterministic validators
Check schema, referential integrity, truth consistency, permission arithmetic, protocol state mapping, graph invariants, exposure reachability, solvable control, action budget and no forbidden truth leakage.

### 5.2 Semantic validators
Check that language preserves intended proposition/role, attack cue is neither absent nor explicit benchmark leakage, difficulty intent is plausible, evidence conflict is coherent, control/attack pair remains comparable, and task is understandable.

Complex semantic cases may require two validators. Material disagreement routes to arbitration or regeneration.

## 6. Repair policy

A candidate may receive one bounded automatic repair when the defect is local and semantics are preserved. Repeated patching is prohibited; regenerate from the skeleton instead.

## 7. Deduplication

Deduplicate at:
- exact normalized text hash;
- structural skeleton signature;
- proposition/evidence graph signature;
- semantic near-duplicate similarity threshold.

Keep rejected-candidate provenance.

## 8. Difficulty calibration

Difficulty labels are not accepted solely from the generator. Use measurable case features plus optional pilot behavior. Maintain a versioned calibration rule per suite. Rebalancing a frozen dataset requires a new version.

## 9. Freeze

A dataset freezes only when:
- target strata/coverage satisfied;
- all accepted cases pass quality gates;
- hashes and provenance complete;
- no Oracle leakage found;
- all controls are solvable;
- all risk cases prove risk exposure reachability;
- case ids stable;
- manifest content hash recorded.

## 10. Lifecycle states

`DRAFT -> GENERATING -> VALIDATING -> CALIBRATING -> READY_TO_FREEZE -> FROZEN -> DEPRECATED`

`FROZEN` is immutable. Corrections create a patch/minor/major version according to governance rules.

## 11. Development sequencing

Datasets are generated incrementally with suite implementation: T311 first, then T312, etc. Do not pre-generate all 18 suites before their executors/scorers can validate them end-to-end.
